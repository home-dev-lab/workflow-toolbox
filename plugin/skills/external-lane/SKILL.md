# External lane

Use an external lane for a complete implementation or review, not a five-minute harness task.

1. Create a dedicated Git worktree and a brief file at .lane/brief.md inside it. Paste the definition of done verbatim, list invariants and exact gates, require detached gates with `EXIT=` markers, require a lane report, and end with `## Lessons for the memory`.
2. Confirm account/project consent. Install the stable launcher with `node plugin/skills/adopt/scripts/install.mjs --set scripts --install --global`; it installs `<configDir>/scripts/wt-lane.mjs`. The plugin-cache `plugin/bin/wt-lane.mjs` works too but changes with plugin upgrades.
3. Launch: `node "$CLAUDE_CONFIG_DIR/scripts/wt-lane.mjs" --dir <worktree> --model <provider/model> --brief <worktree>/.lane/brief.md --timeout 5400`. Re-adopt the launcher after supervision upgrades; a new copy refuses an older installed plugin clearly. `--timeout` is an owner decision bound, not a kill timer; `--decision-grace 300` controls how long the owner has before the default, and `--max-extensions 3` bounds repeated extension defaults before abandon. Configure `lane_models` and `lane_skills` in the plugin's Claude Code settings; both accept comma- or newline-separated values. `WT_LANE_MODELS` and `WT_LANE_SKILLS` remain environment fallbacks when their plugin option is absent. A plugin option always wins over its env fallback. The launcher copies only declared skills into `.lane/` and exposes them with a lane-local `OPENCODE_CONFIG` `skills.paths` file; `save-memory`, `planka-tracking`, and `what-next` are always refused because lanes cannot write shared memory or boards.
4. Monitor with the allow-covered waiter: `Monitor({command: 'node <configDir>/scripts/wt-lane-wait.mjs --dir <wt>'})`. The matching rule is `Bash(node <configDir>/scripts/wt-lane-wait.mjs:*)`; an allow rule covers the command a Monitor runs. It waits for the launcher's worker pid and the terminal `EXIT=` marker, then propagates the lane exit code. A report is input, not proof.
5. Read the report and diff-read the worktree. Run real required gates on that tree, detached with independent `EXIT=` logs. Never re-gate less than once on the real tree. Then commit and merge normally.

On Linux the lane runs in a bubblewrap sandbox: only the worktree, the toolchain, and the CLI's own config and credentials are visible, never `~/.ssh`, `~/.claude`, `/run/user/<uid>` or other processes. The run log's `stage=sandbox` line says whether this launch was sandboxed. When a lane genuinely needs another path, set `WT_LANE_SANDBOX_READ` or `WT_LANE_SANDBOX_WRITE` (colon-separated absolute paths) in the environment that runs `wt-lane.mjs`; never disable the sandbox to fix a missing path. Without `bwrap`, the launcher says so in one line and runs with the environment allow-list only.

The narrow allow rules are `Bash(node /home/<user>/.claude/scripts/wt-lane.mjs:*)` and `Bash(node /home/<user>/.claude/scripts/wt-lane-wait.mjs:*)`. The launcher passes `--auto`, closes stdin, uses the explicit directory, and uses the toolbox-wide OpenCode fence: every child forces omission of Claude Code skill roots. At launch, an uncached and bounded `opencode debug skill` probe runs with the child's exact environment, directory, and config; any effective `save-memory`, `planka-tracking`, or `what-next` discovery (including case and `_`/`-` variants), or any failed probe, refuses the launch. Inherited `OPENCODE_CONFIG` is dropped. The probe is a checked-at-launch filesystem snapshot: local filesystem changes after it completes can change later discovery, and this fence does not attempt to defend against an actor racing local writes. Requested skills are rebuilt under `.lane/` from validated, non-symlink trees whose root frontmatter name matches the requested directory and which contain no nested `SKILL.md`. It writes `.lane/pid`, one `.lane/supervision/<runId>.json` record per run, and an atomic `current.json` pointer. A timeout leaves live work running. Session and pilot owners may choose only `extend` or `abandon`. To relaunch from the worktree's current state, run `node plugin/bin/wt-lane-control.mjs --dir <worktree> --decision abandon`, then start a fresh lane with `node "$CLAUDE_CONFIG_DIR/scripts/wt-lane.mjs" --dir <worktree> --model <provider/model> --brief <file>`; abandonment keeps worktree files intact. Owner ids and tokens prevent accidents but are not authentication. The always-on watcher is observe-only by default and routes attributable notices only to a matching session; unattributable warnings remain project-scoped, and stdout notices are independent of journal success. The SDK lifecycle returns pilot evidence and its control token directly to the pilot. Codex brokers are observed but never cleanup candidates because idleness detection is not implemented. On POSIX the waiter checks liveness with `kill -0`; on Windows it uses the platform process-list path. Consent and saturation hooks recognize `node .../wt-lane.mjs`; activity observes the real `opencode` process and attributes it to its worktree. Never use a harness-managed isolated worktree for a lane: its cleaner can remove an unchanged tree while the detached process is writing.
