# Known issues & open items

The toolkit is **directly usable**: the committed artifacts under
`toolkit/workflows/` launch via `scriptPath` with no toolchain, and a real
39-agent review run validated the full chain end to end. Nothing below blocks
local use.

## Open items

| # | Issue | Impact | Status |
|---|---|---|---|
| 1 | **`budgetFloor` calibration is a cross-run approximation** — the semantics are implemented and tested, and a mechanism ships to ground the number in real runs, but the runtime exposes no per-agent token primitive, so tokens-per-agent stays a statistical estimate. | Floors may cut too early or too late until enough real runs accrue. | `pnpm wt:calibrate record` captures a real run's agent count + `rt.budget.spent()` + the notification token `usage`; `derive` segregates the two signals (never blends them) and prints `floor ≈ tokens-per-agent × (claims × votes + synthesis) × margin`, or an honest "no signal" rather than a fabricated number. The figure is a lower bound — refine it once ~10 real runs accrue. |
| 2 | **The tool-denial / degraded-run indicator is a precision-first heuristic, and its absence is shown as "clean".** `classifyDenial` matches a CLOSED allow-list of three grounded English denial wordings (auto-mode classifier / generic rejection / PreToolUse hook), gated on `is_error===true` — precision over recall, so an ordinary tool error never false-alarms. observe-ui surfaces it **live**: the transcript scan re-runs incrementally as the run streams (denials are transcript-derived — not in the journal or the live SDK stream — so the server scans the growing transcripts per update, and `ingest()`'s own report takes over at the terminal upgrade): a run-level ⚠ DEGRADED pill + per-phase ⚠ badge + the `wt-report`/zip "Tool denials" section, all driven by the same scan. The scan is also recovery-aware: a denial later followed by a plausible successful equivalent (same agent) is counted as recovered and **softens the warning wording without removing the denial**. | If Claude Code ever changes a denial's wording, the matcher returns null and a genuinely-blinded run renders with **no** indicator — and because the UI shows degraded-ness only when detected, that absence reads as a positive "clean" (a false assurance, the dangerous direction). Per-phase badges also can't place a denial on a **phaseless/unattributed** agent (the run-level pill + the panel's "(unattributed)" group still count it). | Mitigated, not eliminated: the wordings are unit-pinned to the exact captured strings (`debugger/test/tool-denial.test.ts`), the `ingest()→denials` path is now covered by an ingest integration test in the Workflow Observatory repo, and both the single-run and the **pipeline combined view** thread the same report so the UI and the downloadable report agree. A live wording-drift would still pass silently — re-running the **`upgrade-canary`** after a Claude Code upgrade is the intended trip-wire; treat a sudden drop to "no denials ever" on a run you watched get blocked as the signal to re-ground the allow-list. |
| 3 | **Windows/macOS support  ships with accepted platform semantics, untested on real hardware.** (a) `chmod 0600/0700` on the pidfile/state dirs is a near-no-op on Windows (NTFS ACLs, not POSIX modes) — the pidfile's API token is protected by the user-profile ACL of `%LOCALAPPDATA%`, not by mode bits. (b) `wt-observe stop`'s SIGTERM is a HARD terminate on Windows (no graceful-shutdown signal exists) — the server's exit-path cleanup does not run there — specifically the owned vite-watcher reap and the graceful host close. (SDK children of launched runs are unaffected: on every platform they are deliberately left to outlive the server and are re-adopted by the launch-resume sweep at the next enabled boot.) (c) The win32 PID-identity probes shell out to PowerShell (~1s per probe) — `status`/`start`/`stop` are that much slower. (d) An npm-installed `claude.cmd` shim is NOT found by the bare-`claude` PATH probe (CreateProcess resolves `.exe` only) — set `CLAUDE_BIN` to the shim's `.cmd` path explicitly instead (as of the cross-OS CI fixes, `resolveClaudeRuntime` spawns a `.cmd`/`.bat` `CLAUDE_BIN` via `shell:true` — previously this also silently fell through, same as the bare-PATH gap). | Mac/Windows users get native state/config locations, working spawns and recycled-PID protection, but the four semantics above differ from Linux, and none of this has run on a real macOS/Windows machine yet. | Code paths are unit-tested via injected `platform`/parsers; the impure probes are best-effort with 3s timeouts (degrade to identity-unknown, the safe direction). Validated since: a cross-OS CI matrix (`.github/workflows/cross-os.yml` — full test suite + lifecycle smoke on real windows/macos/ubuntu runners) AND an end-to-end native-Windows session (2026-07-08: native state root, PID identity, real-credential launch with live DAG, terminal-close survival — see the windows-native guide shipped with Workflow Observatory). macOS still lacks a real-credentials manual pass; semantics (a)-(d) remain by-design differences. |
| 4 | **The per-run `capabilities` args section needs a companion server new enough to compose it.** `wt-observe launch --args '{"capabilities": {...}}'` validates a `{ mcpServers?, agents?, skills? }` section early and loudly (shared contract: `toolkit/packages/debugger/src/capabilities.ts`; composition semantics e2e-proven by `packages/smoke/src/capabilities-probe.ts`), and up-to-date Workflow Observatory servers now compose the validated section into the delegated run's `query()` options (after the server's own `settingSources`/`strictMcpConfig` posture) — per-run MCP servers, per-role agent identities, and skill filters work end to end on that pairing. The remaining coupling is version skew: an OLDER companion server accepts the launch and silently ignores the section — the launcher's stderr note ("older servers ignore it") is the tripwire. Agent-frontmatter `mcpServers:` remains outside this path; declare per-agent MCP servers through the args `capabilities.agents` entries, the supported channel. | With a current companion server the section works end to end. Against an older server it validates, then is ignored (see the stderr note) — custom agents there run identity+allowlist only. | Both halves shipped: launcher validation here, server-side composition in the companion app. Keep launcher and server in step; treat the stderr note as the skew warning. |
| 5 | **`wt-observe launch` refuses the launch (non-zero exit) when a capability sidecar cannot be resolved** — rather than launching a role half-equipped. It refuses when a `<workflow>.capabilities.json` sidecar is present but unreadable or not valid JSON, when the machine capability registry itself is invalid, when a **required** (non-`optional`) need resolves to no provider and no tool-yielding fallback, or when a provider config needs `$CWD` but the requester's directory is unknown. Every problem is listed at once (`toolkit/packages/debugger/src/{capability-registry,launch-capabilities}.ts`). Observer `requires` are the deliberate contrast: an unresolved observer need never fails the launch — the observer is simply not attached (an observer is peripheral). | A role whose defining capability cannot be provided at all won't run pretending it has the tool; the operator sees exactly what to register. A missing sidecar is a silent no-op — capabilities are opt-in. | By design (fail-loud on the constitutive path, degrade on the peripheral one). To run degraded on purpose, mark the need `optional: true`; to resolve it, register a provider — see [`docs/public/capability-registry.md`](capability-registry.md). |
| 6 | **Custom-observer capability resolution needs the launcher and the companion server on matching versions of the shared observers contract.** An observer's abstract `requires` are resolved by the **launcher** into `args.observers[i].resolution` (the server never resolves — it only composes the stored resolution into the brain at tick time). That field is validated by the shared `observer-def.ts` contract, where unknown keys fail loud. So the skew cuts both ways: a launcher NEWER than the server (whose contract predates the `resolution` field) is refused with `400 … resolution is not a known field`; a launcher OLDER than the server emits no `resolution`, so an inline observer's `requires` are never resolved and the observer is not attached when a need is required. | Version skew of the shared observers contract either refuses the launch or silently drops a required-tooled observer. | Keep the `wt-observe` launcher and the companion Workflow Observatory server on matching versions of the shared `observer-def.ts` contract — the same discipline as the `capabilities` skew in item 4. |
| 7 | **A custom observer's proactive hints only reach LONG-running observed agents.** The observer mechanism is out-of-band and periodic — a tick fires on the registered cadence (a one-minute floor, a ten-minute default), then a (possibly tooled) brain runs and the observed agent consults its hints at a natural boundary, so the end-to-end proactive path is minutes-scale. A short fan-out agent completes before a hint could be delivered. | An observer attached to short-lived agents still produces durable summaries, but its `observer.hint` delivery does not land in time to steer them. | By design for v0 — the reference `docs-butler` example targets long-running implementer agents. Covering short agents needs a synchronous, pause-based delivery path (future work); a run is never failed by an observer either way. |
| 8 | **The observer-consumer teaching brief is not yet auto-delivered to observed roles.** When an observer emits `wt-comm` hints, the observed agents need the observed-role consumer section of the teaching pack (`toolkit/packages/comm/teaching/wt-comm-observer-consumer.md`) referenced in their prompts so they consult hints at natural boundaries. Today the workflow **author** must reference that section into the observed roles' prompts by hand (reference, never copy — it is parameterized with the run's comm dir + role id at run time). Automatic injection of the section by the composer (to the roles matched by `watch.roles`), and the runtime parameterization it needs, are **not yet wired**. | An observed role whose prompt does not reference the consumer brief will not know to consult its hints. The wt-comm hint-**delivery** channel itself works (`wt-observe launch --comm-root <dir>` writes the hints); only the steering brief must be added by hand. | Future work — the composer emits the observer-consumer section to the roles matched by `watch.roles`, and the runtime parameterizes it at attach (the design's channel (a)). Until then, add the reference by hand; a run is never failed by a missing brief. |




## External limitations — mitigated, not fixable here

| # | Limitation | Mitigation |
|---|---|---|
| A | **The Workflow tool is a research preview**; part of the surface the toolkit relies on (`isolation`, `label`, `budget`, the determinism bans, the 512 KB cap) is verified against the binary, not officially documented. An upgrade can change it. | Firewalled behind `@workflow-toolbox/runtime` — exactly one package changes. Re-verify after upgrades; the `upgrade-canary` skill does exactly this. |
| B | **Silent exclusion over 512 KB** on the `name` path: an oversized file in `.claude/workflows/` is simply never registered — no error anywhere. | `workflow-toolbox build` warns from 400 KB and throws at 512 KB. Hand-edited artifacts past the cap remain a blind spot. |
| C | **The name registry refreshes lazily** — invocation by `name` can fail right after install. | Use `scriptPath`, which is always reliable; documented in the README. |
| D | **Agents die mid-reasoning at context limits — systematically.** Several occurrences during development; the dying agent's last mid-thought text arrives as a normal-looking completion. | The four defence layers encoded in the examples + README: a schema at every consumed boundary, fresh-evidence verification, decomposed agent scopes, and `WorkflowOutput.error` + `resumeFromRunId`. A discipline, not a fix. |
| E | **Top-tier model alias availability is environment- and time-dependent** (plan tiers, access windows, provider policy — `'fable'` has already gone through availability churn) — a verifier (or any agent) pinned to an alias that is not callable where the run executes errors at runtime. | `BEST_MODEL` tracks the strongest *reliably-callable* tier (currently `'opus'`), so `adversarialVerification` verifiers default to a safe tier; the toolkit never pins a volatile alias itself. Verify an alias is callable in the run environment before hand-overriding any `model`/`verifierModel`; bump `BEST_MODEL` when the reliably-callable tier changes. |
| F | **`dev-implement` `{artifactPath}` very-large-file fidelity** — in `artifactPath` mode the PlanArtifact is read by an agent (the sandbox has no filesystem) and returned through the agent's output. A very large artifact (the JSDoc cites ~60 KB as the motivating case) could in principle be truncated or reworded by the agent. | **Fails loud, never silent-wrong**: a truncated read yields invalid JSON (caught at `JSON.parse`) and structural corruption is caught by the same `validateArtifact`/`validateGraph` gate the inline path uses. The only undetectable residue is a paraphrased *string* field that still parses, whose blast radius is a slightly degraded implementer prompt (the fresh-evidence checker reads real test output, not the prompt). If a large artifact intermittently fails to load, re-run, or inline it via `{ artifact }`. **Path base**: an absolute `artifactPath` is unambiguous; a relative one resolves against the read agent's cwd (the Claude Code session dir, verified live 2026-06-21), *not* the artifact's `projectDir` — prefer absolute. |
