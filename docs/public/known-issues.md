# Known issues & open items

The toolkit is **directly usable**: the committed artifacts under
`toolkit/workflows/` launch via `scriptPath` with no toolchain, and a real
39-agent review run validated the full chain end to end. Nothing below blocks
local use.

## Spawn Registry Surfaces

- `plugin/bin/wt-session-start-registry-hook.mjs` runs the registry scan on `SessionStart` using the hook payload's own `session_id`, so it checks the current session's journal even when the state directory contains several journals.
- `plugin/bin/wt-spawn-registry-scan.mjs` is the manual read/ack CLI for those journals. With exactly one journal it behaves as before. With multiple journals it refuses an ambiguous read or `--ack` unless `--session <id>` is supplied, using exit code `3` so ambiguity stays distinct from `2` (`no registry`).
- The operator-facing commands therefore include the session explicitly: `node plugin/bin/wt-spawn-registry-scan.mjs --session <id> --quiet-min 20` for a manual scan, and `node plugin/bin/wt-spawn-registry-scan.mjs --session <id> --ack <name>` after you have checked a surfaced entry.

## Shipped Hooks, Guards & Monitors

Hooks and monitors shipped under `plugin/bin/` that are not already covered by a section above:
what fires them, what they check, and their output/exit contract.

### `wt-adopt-check-hook.mjs` — rule-adoption state check (SessionStart + PostToolUse)

Checks BOTH managed sets — `.claude/rules/` and `.claude/agents/` — in the project AND global config dirs, by running the adopt installer in `--check` mode and reusing its absent, clean, stale, edited, symlink, and hand-authored classification. A file counts as OK if either the project or the global copy is current (the union, not an intersection), so an adopted-globally rule never falsely reads as absent. It is silent when everything checked is adopted and current; otherwise it names the absent/stale/edited files per set and suggests the adoption fix (for agents, only `stale` is a finding — the pilot suite's project copies are opt-in by design). It never installs or changes anything: adoption requires the owner's consent. Besides SessionStart, it also re-fires on PostToolUse after a `git push` — the moment the shipped rules can move ahead of the adopted copies — with a preface explaining why the notice appears mid-session. Any internal error exits 0 silently so it cannot break a session or a push.

### `wt-arc-watch.mjs` — delegated-agent transcript watcher (monitor)

Watches subagent transcripts for the current project's sessions and emits only when a transcript has stopped growing or disappeared. It stays silent while agents are writing, so silence means the watched agents are still working. It does not treat staleness as proof of death: a waiting agent can be stale too. It withholds all output until this session has delegated at least once, and never self-terminates while waiting so a later delegation remains covered.

### `wt-lesson-harvest-hook.mjs` — closure-report lesson surfacing (Stop)

At each turn end it walks the project's report directories (`.claude/reports`, `.claude/pilots` by default, overridable with `WT_LESSON_HARVEST_DIRS`), runs the bundled `lesson-harvest` extractor over any markdown report it has not already seen at that modification time, and emits one advisory naming the reports that carry lessons and how many. It records every file examined — including reports with no lessons — so the same walk is not repeated at every turn end, and it speaks again for a report that changes, because a rewritten report is new material. `WT_LESSON_HARVEST_OFF` disables it.

It **only surfaces**. It never writes to a knowledge base: deciding what becomes a durable note, under what name, deduplicated against what already exists, stays with the single session that integrates the card — the constraint the extractor itself was built around. It names the report paths rather than the lesson text, because a Stop hook's output is visible to the human as well as the model and several verbatim lessons per turn end would become the thing people silence.

⚠ **Honest scope, and the uncovered half is the larger one.** This covers lessons that reached a REPORT. A correction arriving mid-conversation has no report to harvest from, and the hook's existence must not be read as full coverage. A report with no lessons section at all, and an unreadable one, both stay silent by design — the overwhelming majority of markdown a report tree contains is neither, and a hook that spoke about each would be switched off within a day, taking its real case with it.

### `wt-autonomy-arm.mjs` — autonomy mandate declaration (standalone CLI)

Writes, withdraws or reports the **project-keyed** marker `engine-<projectSlug>.json` that `wt-autonomy-watch.mjs` refuses to run without, under `${XDG_STATE_HOME:-$HOME/.local/state}/wt-queue-gate/` (overridable by `WT_AUTONOMY_WATCH_MANDATE_DIR`, resolved identically by both scripts). Run with no argument it arms the current directory's project (`--project <dir>` targets another), `--disarm` withdraws, `--status` reports without writing. The exit code carries the verdict so a caller need not parse prose: 0 armed and live, 1 no marker at all, 2 for a usage error or a missing `CLAUDE_CODE_SESSION_ID` (which it refuses to guess rather than write a marker nothing will read), 3 a marker exists but is **expired** — present on disk, past the freshness window, will not fire.

It is deliberately **not a hook**. A hook stamping the marker at session start would declare a mandate for every session whether or not anyone wanted one, reintroducing exactly the noise the watcher's mandate gate exists to prevent — declaring a mandate is an act, and this is the act.

The marker is keyed on the **project**, not the session — this was fixed after shipping: a per-session key died the instant its session restarted (a restart mints a new `CLAUDE_CODE_SESSION_ID`, so the old marker became permanently unreachable), leaving a restarted session that believed it still held a mandate silently unable to ever be woken. Keying on the project instead means a restarted session inherits whatever mandate is still fresh for that project, with no gesture. That inheritance is bounded by a **freshness window** (default 8h, `WT_AUTONOMY_WATCH_MANDATE_FRESHNESS_MINUTES`), read from the marker's own `declaredAtMs` field rather than its mtime: past the window the marker stops counting on its own. The trade this accepts is a stale mandate that could in principle wake a session after the human stopped caring — but that failure is **loud and killable** (the wake is visible in the transcript, `--disarm` clears it), where the per-session scheme's failure was silent and permanent. See `plugin/autonomy/AUTONOMY.md` for the argument in full, and the section immediately below for how the watcher announces the inheritance.

`--status` and the watcher's arming banner used to each carry their own freshness check, and they disagreed about the exact same marker at the exact same instant: the watcher correctly refused an expired mandate (`mandate=stale(540min) · CANNOT FIRE`) while `--status` still reported `armed`, because it only checked the marker's existence. Both readouts now call one shared classifier (`plugin/bin/lib/autonomy-mandate.mjs`), so `--status` reports exactly one of three states — `armed` (live), `expired` (present, past the window, will not fire — re-arm with no arguments), or `not armed` (nothing declared) — and can no longer say `armed` about a mandate the watcher would refuse to honour.

### `wt-autonomy-watch.mjs` — idle-autonomy wake monitor (monitor)

Watches only projects that have explicitly declared an autonomy mandate by writing `engine-<projectSlug>.json` under `${XDG_STATE_HOME:-$HOME/.local/state}/wt-queue-gate/`. With no mandate marker it emits nothing, ever; with one older than the freshness window it treats it as stale and stays equally silent — its banner distinguishes `mandate=absent` from `mandate=stale(NNmin)`, because the two call for different remedies. With a fresh mandate present it wakes only when the queue snapshot at the same state root is fresh and says actionable work remains, the CURRENT session's own transcript has been idle past the configured threshold, and nothing else is in flight: no recently-written delegate transcript for that session and no external lane process still running in the same project. It emits once per idle stretch, writes its own per-session marker file so a missed wake can be distinguished from a watcher that never fired, and re-arms only after the session transcript grows or the mandate marker is refreshed. Missing, stale, unreadable, or malformed queue data is treated as unknown and stays silent rather than waking on a guess.

Because the mandate marker is project-keyed, the session that wakes is not always the one that declared the mandate — a restart is the common case. When it isn't, the wake line and the arming banner both say so explicitly (`mandate=present(inherited)`, and the wake reads `... idle session with mandate (inherited from session <id>, mandate declared NNmin ago), ...`), rather than letting a session discover only that "something woke me".

### `wt-check-commit-signatures-hook.mjs` — commit-signature dual gate (PostToolUse + PreToolUse)

Wraps `wt-check-commit-signatures.mjs` at two different points around `git`. After a `git commit` Bash command has already run, it re-checks `HEAD` and, if unsigned, emits a PostToolUse advisory (`additionalContext`) naming the problem — the commit already landed, so this path never blocks. Before a `git push` runs, it derives the outgoing commit range(s) from the push's remote and refspecs and denies the push (`permissionDecision: 'deny'`) only on CONFIRMED unsigned offenders in that range; anything uncertain — no derivable range, a Git error, a malformed push shape — fails open rather than blocking. The goal is an earlier, cheaper failure than the remote's own rejection of the same push.

### `wt-check-commit-signatures.mjs` — commit-signature verifier (standalone CLI)

Checks whether signing is expected from `commit.gpgsign` or `user.signingkey`, then inspects `HEAD` or the supplied revision range with Git's signature status. It exits 0 when signing is not expected or no offending commits are found, exits 1 after printing offending commits and remediation guidance, and exits 2 for argument or Git usage errors. It accepts `--repo` and `--range`; unknown arguments and missing flag values are errors.

### `wt-lane-saturation-hook.mjs` — external-lane contention guard (PreToolUse on Bash)

Fires only on a command that actually invokes an external executor lane (`opencode run`, `codex exec`) — a command that merely mentions one (a grep, a quoted string, a shell comment) is ignored. It counts live lane processes and, when this call would put the total at or past the bound, **refuses it**: `hookSpecificOutput.permissionDecision:'deny'`, for any Bash caller including the main session. This is the default as of plugin 0.118.0 — an earlier version warned and allowed the call through, which was measured to be insufficient: an informed caller can read a warning and proceed anyway, and the founding incident below was never a lack of information. Set `WT_LANE_ENFORCE_MODE=warn` to fall back to the old advisory-only behavior instantly, with no code change, if the deny default proves too aggressive. The problem it addresses is that a lane is a shared resource nobody reserves: every arc sees only its own calls, so two concurrent arcs both observe "it's slow, nothing comes back" and neither can reach the cause, because the cause is in the other one. Past the bound the lane does not refuse cleanly on its own — it rate-limits and retries (latency roughly 5–8×), and then the **caller's own timeout** converts that slowdown into a dead call, which is how the founding incident lost four batches. The bound is a named parameter, `WT_LANE_MAX_CONCURRENT` (default 8, the low end of a measured 8–16 wall that moves with the subscribed plan). Counting is by **exact process name**, not by command-line match: a command-line match counts the shells that merely carry the string — measured on a machine with zero lane calls running, the command-line form returned 2 while the exact-name form correctly returned 0. If the counting tool is unavailable the hook reports that usage was **NOT MEASURED** and never denies on that basis — a measurement failure is grounds to warn, never to block. ⚠ The check-then-act count has no lock: two truly simultaneous calls can both observe the same live count and both be allowed, landing one over the bound — a real, disclosed limitation, not a rounding error (see the hook's own header comment).

### `wt-lane-consent-gate-hook.mjs` — external-lane consent gate (PreToolUse on Bash)

Fires only on a command that actually invokes an external executor lane (`opencode run`, `codex exec` — the same quote/comment-stripped detection as `wt-lane-saturation-hook.mjs`) and refuses it (`permissionDecision:'deny'`) unless the `WT_EXECUTOR_LANE_CONSENT` switch resolves to consented for the current account/project pair. It is the enforcement counterpart to `wt-lane-consent-check-hook.mjs`: that hook only warns at session start when auto-loaded rules disagree with the switch, and neither the lane-verifier agents nor the pilot-wave skill's own prose ever consulted the switch at the moment a call actually runs — an instruction a model can silently skip is not a gate. This hook is the gate: it inspects the account settings ceiling, then the project settings narrowing, and denies unless both resolve to `"true"`/no-narrowing, naming which level refused. **It fails CLOSED, not open** — the deliberate exception among this file's guards: an unreadable or malformed settings file is treated exactly like "not consented" rather than silently granting the call, and the hook's own internal errors resolve to a denial rather than an allow, because a consent switch that fails open on error grants permission it was never given. It never widens what a project's rules describe as policy — it only makes the existing opt-in switch enforceable at the one place it previously had no effect.

### `wt-env-prerequisite-drift-hook.mjs` — post-adoption environment drift light (SessionStart)

Re-checks, at every session start, that the environment settings the adopted sets require are still DECLARED in the active config profile's `settings.json`. `adopt` writes them on the day you adopt; nothing re-checks afterwards, so a settings file edited later — by you, by another tool, by a machine restore — silently degrades the plugin: without the nested-spawn depth key an executor lane can die mid-wave, and without the observer flag adopted pilots run with no watchdog while their reports honestly say "no observer findings". It is a warning light, never a gate: it always exits `0`. Three states, never a boolean — a settings file it cannot read or parse is reported as **NOT CHECKED**, explicitly not as "absent", because folding "I could not measure" into "it is broken" is how a session-start check earns a reputation for crying wolf. It is silent when every prerequisite is present, and silent for a project that adopted nothing (a project with its own hand-written agents has no observer prerequisite — adoption is detected by the installer's banner in `.claude/rules`/`.claude/agents`, never by the directory merely existing). When it does speak it names the key, the concrete consequence, and the way out in both directions: run the installer, or declare the key yourself with any value you prefer — it checks that a key is declared, never what it holds. **No environment value ever reaches its output**, since that block carries real credentials; it reads key names only.

### `wt-hook-registration-drift-hook.mjs` — stale hook-registration detector (SessionStart + UserPromptSubmit)

At SessionStart it resolves every `${CLAUDE_PLUGIN_ROOT}` hook path the current manifest declares and writes that exact set to a small per-session state file. On each later UserPromptSubmit it re-checks those recorded absolute paths against the filesystem. Clean checks stay silent and leave the file untouched. If any recorded path has disappeared, it emits one `additionalContext` naming the missing hook files by event and basename, states plainly that this session's in-memory hook registration is stale, and says the limit honestly: it cannot repair itself mid-session, only a session restart picks up the corrected manifest. It records `reportedAt` after that first notice so the same session is not warned again on every turn.

It does not close the underlying failure — the hook whose file went missing still crashes unattributed on its own next invocation, since the module-loader error happens before any of its code runs. It cannot detect its own file going missing either: if this hook itself is renamed or deleted, the running session's next `UserPromptSubmit` fails the same unattributed way (the existing shim convention used for the `wt-adopt-check-hook.mjs` rename covers this case, should it ever arise). Two `UserPromptSubmit` invocations racing within the same session, or two session ids colliding after sanitization, are theoretical gaps with no dedicated lock — not exploitable under Claude Code's per-session serialized `UserPromptSubmit` execution or with real UUID session ids, but named here rather than left implicit.

### `wt-memory-index-check-hook.mjs` — knowledge-base index probe (SessionStart)

Fires only when `Edit`, `Write`, or `MultiEdit` touches a file under a `.claude`- (or

### `wt-rule-convention-guard-hook.mjs` — rule-writing-convention blocker (PreToolUse)

**This one REFUSES the write** — it is the only shipped hook that does, so know what it costs
you before adopting the plugin.

It fires on `Edit`, `Write`, or `MultiEdit` against a rule file (`.md` one or two levels under
a directory named `rules`) or an agent definition (`.md` directly under `agents` or
`agent-templates`). It inspects ONLY the text being ADDED — never the file as it stands — and
denies the call when that text carries a calendar date, a person's name, or a narrative
formula such as "standing instruction from". The reason it returns names the detector, the
exact matched text, and the offending line.

The invariant behind it: a rule states what to DO plus the invariant that makes it right. The
date, the name, and the story of how the rule came to exist belong in a note, and a rule that
accumulates them stops being read.

**Why it inspects the addition rather than the file**: many existing rule sets already contain
dates and names. Checking the whole file would refuse every edit to such a file — including the
edits that REMOVE the offending text — so the guard would block its own remedy.

**Escape hatch**: a line carrying `<!-- rule-lint: allow -->` is exempt. A rule may legitimately
need to quote a dated example verbatim, and a guard with no exit gets disabled wholesale the
first time it is wrong.

**What it deliberately does NOT check**: writing style, sentence length, and whether a
compression lost a nuance. Those need judgment, and a mechanical guard that attempted them
would refuse correct work.

Internal errors fail open — the guard emits nothing, exits 0, and writes one line to stderr
naming itself. A guard that failed closed on its own bug would block all rule editing.

### `wt-command-repeat-check.mjs` — repeated-command result detector (standalone CLI)

Records one executed command/result pair and flags it on two independent axes once either has recurred at least 3 times (the default threshold) in one project/session — the third occurrence and every one after it, not only the third. It is not registered as a hook, so projects can verify its behavior before choosing where to arm it.

- **Shape axis**: the exact same normalized command TEXT producing the exact same result. Catches a literal retry loop.
- **Class axis**: the same VERB and FLAG SET (literal positional/quoted arguments ignored, flag order normalized, `--key=value` long-flag values stripped, a bare `--` end-of-options terminator respected) producing the same coarse HOLLOW/non-hollow verdict — hollow meaning empty stdout, or stdout exactly `0`, with a real populated stderr on exit 1 always treated as a genuine error rather than hollow. Catches "the same style of check, run against a shifting target, keeps coming up empty" (e.g. three different `grep -c '<pattern>' <file>` calls, three different patterns, all returning `0`) — a pattern the shape axis structurally cannot see. It does NOT unify hollow checks across different verbs (a `find` and a `pgrep` and a `grep`, each returning nothing once, stay on separate, silent counters) — that would need semantic classification of intent, which this tool deliberately does not attempt.

Required inputs are `--session`, `--command`, and `--exit-code`; it also accepts `--cwd`, `--stdout`, `--stderr`, `--signal`, `--stdout-file`, `--stderr-file`, `--at`, `--state-dir`, `--threshold`, `--class-threshold`, `--ttl-ms`, `--max-pairs`, `--max-class-shapes`, and `--json`. Missing required values, invalid numeric values, and unknown arguments exit 2.

### `wt-unquoted-tool-glob-guard-hook.mjs` — unquoted tool-option glob blocker (PreToolUse on Bash)

Denies a Bash command that passes a glob pattern to a narrow set of tool OPTIONS unquoted — `grep --include=*.ts`, `find -name *.mjs`, `--exclude=*.log`, `-path */node_modules/*` — and nothing else. In zsh a glob with no match is a hard error that aborts the command before any redirection, so the command produces nothing and the emptiness reads as a real finding ("no hits", "not registered", "absent"); if it does match, the shell expands it against the current directory and the tool silently receives concrete filenames instead of the pattern. Both outcomes are wrong, and there is no case where one of the covered flags is meant to take an unquoted glob — which is why this guard blocks (`permissionDecision: 'deny'`) rather than only warning.

It strips heredoc bodies, backtick spans, and quoted spans before matching, so a command that merely documents or discusses the pattern — in a commit message, a heredoc, an already-quoted example — is left alone. It ships blocking on the strength of a measurement run before it shipped: 5,193 session transcripts, 82,015 Bash commands, 206 distinct commands matching the option-value glob shape, each replayed against the guard's own executable as a real PreToolUse payload — 197 true positives, 0 false positives, 9 correct silences, on material the guard never chose.

It deliberately does not cover a bare unquoted glob as an ordinary shell argument (`ls path/prefix*`, `for f in *.md`), where unquoted is normally what the author meant; flagging that class is the false-positive shape that gets a guard switched off. It also says nothing about the sibling zsh traps of unquoted word-splitting or `$var:path` being read as a parameter modifier rather than concatenation, and it only inspects Bash tool calls under a zsh-shaped hazard model — the silent-expansion half of the risk still applies under other shells even where the hard-abort half does not.

### `wt-var-colon-modifier-guard-hook.mjs` — bare `$var:` parameter-modifier warner (PreToolUse on Bash)

Warns (never blocks) when a double-quoted Bash string contains a bare, unbraced `$var:letter` where `letter` is one of the 13 standalone parameter-expansion modifiers `man zshexpn` documents (`a A c e h l P q Q r s t u`). In zsh, `:` right after an unbraced parameter name starts a history/modifier expansion rather than being read as literal text — `git show "$s:src/db-base.ts"` fails with `bad substitution`, and the resulting empty command substitution can silently read as "not found" instead of erroring loudly. Safe forms are `"${var}:path"` (braces) or a single-quoted string.

It strips heredoc bodies under a quoted delimiter, single-quoted spans, and backtick spans before matching, so a command that merely documents the pattern is left alone; an unquoted heredoc delimiter still expands its body and is left in place for the match to see.

It ships warn-only, not blocking: an over-broad 34-letter candidate set produced 22 warnings on 125 matching real commands, of which only 6 were genuine (27% precision); narrowing to the 13 documented modifier letters brought that to 6 warnings, all genuine (100% precision) — a clean result, but on one measured sample, not the blocking bar this repo requires (the sibling unquoted-glob guard's 197 true positives / 0 false positives over 82,015 commands). It deliberately does not cover single-quoted strings or `${var}:...` (both safe, deliberately silent), a letter outside the 13-letter set, an unrecognized letter that zsh's parser skips before finding a real modifier one character later, or anything inside a `$(...)` command substitution.

### `wt-merge-chain-guard-hook.mjs` — merge-then-gate chain warning (PreToolUse on Bash)

Flags (never blocks) a Bash command that chains a `git merge` together with whatever runs after it — `git merge x && pnpm test`, `git merge x ; pnpm test`, or the two on separate lines of one command string. A merge can do nothing — `Already up to date` from the wrong tree, or an abort on a non-fast-forwardable branch — and the chained commands then run on the unmerged tree and return exit 0, so gates read green while certifying a subject nobody intended to certify. The exit code cannot detect this: it belongs to the gate, and the gate genuinely passes, answering a question about the wrong subject. The remedy, stated in the warning, is always the same shape: run the merge alone, read its result, then gate in a separate command.

It strips heredoc bodies, backtick spans, quoted spans, and shell comments before matching, so a command that merely discusses or documents the pattern is left alone. It matches the same `git`/`git -C <dir>` shape `wt-check-commit-signatures-hook.mjs` already uses for `git commit`/`git push`, not a generic `git ... merge ...` scanner — flags other than `-C` between `git` and `merge` are out of scope, and `merge` must be followed by whitespace or end-of-segment so it never matches `git merge-base`/`merge-tree`/`merge-file`, real and unrelated plumbing subcommands.

**It ships WARN-ONLY (`permissionDecision: 'allow'` with a reason, never `'deny'`), and that is a measured decision, not a default caution.** The hazard-matching predicate — any command follows a `git merge` in the same invocation — is exactly what the hazard is, but this project's own history is dominated by a DIFFERENT, safe pattern that the predicate cannot distinguish from a blind chained gate: `git merge x > log 2>&1; echo "merge: $?"; <inspect the log or compare tree hashes>`. Measured against 1,140 distinct real `git merge` Bash commands drawn from this machine's session transcripts, replayed against the guard's own executable as PreToolUse payloads: 376 matched, and reading them showed the large majority were the safe capture-then-inspect pattern rather than a downstream gate trusting the merge blindly — a verb-based re-check (test/build/publish/push present in the chained tail) still found roughly three quarters with no such verb. That is far short of the 0-false-positive bar `wt-unquoted-tool-glob-guard-hook.mjs` cleared before shipping blocking, so this guard warns until a predicate that can tell "diagnostic read of the merge's own result" apart from "gate trusting it blindly" is designed and measured to that bar.

It deliberately does not cover: a `git merge` preceded by other commands (`cd repo && git merge x`), where nothing after the merge can certify a stale tree; `git merge --abort` / `--continue` / `--quit`, which cannot silently no-op the way a plain `git merge <branch>` can; a `git merge` run alone with nothing chained after it; or a merge chained via a subshell/command-substitution boundary the guard does not parse.

### `wt-missing-package-script-guard-hook.mjs` — missing package-manager script warning (PreToolUse on Bash)

Warns (never blocks) when a Bash command invokes a package-manager script — `pnpm <script>`, `npm run <script>`, `yarn <script>` — whose name is not defined in the `scripts` map of the `package.json` that governs the command's effective directory. In a pnpm/npm/yarn workspace, running a workspace-root gate (`pnpm test`, `pnpm lint`) from inside a sub-package that does not define that script fails with a package-manager error and a non-zero exit — and the cost is not the failed command, it is that the failure is indistinguishable from a real regression, most often right after a merge, which is exactly when a false non-zero exit is most costly to misread.

It tracks `cd`/`&&` chains across the command, resolving `cd toolkit && pnpm test` against `toolkit` rather than against the Bash tool call's own reported cwd, cumulatively across several `cd`s in one chain. Resolution is conservative: the moment the effective directory cannot be determined with confidence — `cd -`, a target containing `$` or a backtick, a nonexistent target, or any segment containing `(`/`)` — that segment and every later one in the same chain go untracked, and the guard stays silent for them, though an absolute-path `cd` later in the chain still recovers. This tracking exists because an earlier, untracked version of this guard (in this project's private precursor) warned on a correct `cd toolkit && pnpm test` within minutes of shipping — the dominant real shape, missed by a verification set written alongside the code it was verifying. It strips heredoc bodies, backtick spans, quoted spans, and shell comments before splitting on shell separators, the same discipline `wt-merge-chain-guard-hook.mjs` uses, so a quoted or documented mention of a `pnpm <script>` command is not read as a real chained invocation.

It deliberately does not cover: `pnpm install`/`add`/`exec`/`dlx`, `npx`, or a direct binary path (`node_modules/.bin/vite`) — none of these are script-name lookups; a script that exists but would fail for an unrelated reason (missing dependency, syntax error) — this guard checks name existence only; `cd -`, a `$VAR`/`$(...)` target, a nonexistent `cd` target, or a subshell/command-grouping segment — the effective directory is not confidently known there, so the guard stays silent rather than guess; and workspace-aware flags beyond `-r`/`--recursive`/`-w`/`--workspace-root`/`--filter`/`-C`/`--dir`, which are treated as "resolves elsewhere" and left silent by design.

### `wt-main-guard-hook.mjs` — main-session irreversible-action guard (PreToolUse on Bash)

`wt-pilot-guard-hook.mjs` guards every SUBAGENT against a set of irreversible Bash actions, but it deliberately no-ops when `agent_id` is absent — i.e. for the main session itself, which it treats as the arbiter that already holds the gate. This is that mechanism's mirror image: it acts ONLY when `agent_id` is absent (so the two guards never double-message the user for one command) and only on Bash calls.

**Per-class posture is a measured split, not one verdict for the whole guard.** Four classes ship BLOCKING (`permissionDecision: 'deny'`): `npm`/`pnpm`/`yarn publish`; a force-push (`--force`/`--force-with-lease`); a remote branch deletion (`git push --delete`/`git push origin :branch`); and `rm -rf` targeting the filesystem root or the home directory. Measured against 2,788 distinct real Bash commands drawn from every session transcript on this machine (both config dirs), replayed against the guard's own executable as PreToolUse payloads: publish 16/16 true positives, force-push 13/13, remote branch deletion 4/4 — 0 false positives across all three; root/home `rm -rf` had zero occurrences in the sample and stays blocking structurally (there is no legitimate `rm -rf /` or `rm -rf ~`).

Two further classes matched the same trigger shapes but measured the OPPOSITE way and ship JOURNAL-ONLY (allowed, logged to `~/.local/state/wt-main-guard/journal.jsonl`, never denied): `rm -rf` targeting a git repository root, and `rm -rf` targeting a token that cannot be statically resolved (an unexpanded shell variable or a glob). The git-repository-root class was 10/10 false positives — every match was a disposable `/tmp` clone or a `git worktree` purge about to be recreated, the exact "routine cleanup" case that denying would get the guard bypassed over within a week. The unresolvable-target class was 319 candidates, of which a manual and a heuristic sweep both found the sampled commands to be `rm -rf "$VAR"` where `$VAR` was bound earlier in the SAME multi-line command to a scratch/tmp path (`$(mktemp -d)`, a scratchpad directory) — safe, but invisible to a classifier that evaluates one shell segment at a time and cannot see an earlier assignment. Both classes are still detected and journaled, so the gap is visible on disk rather than silent; re-measuring a predicate that resolves same-command variable assignments before blocking is future work, not done here.

A `git merge` integrating a branch INTO `main`/`master` while the main session is on `main`/`master` is JOURNAL-ONLY by design, not by measurement — the opposite direction from what the pilot guard blocks, and legitimate for the arbiter to do; it is recorded for traceability, never refused. An ordinary `rm -rf` on a ordinary target (neither catastrophic nor unresolvable) is likewise journal-only.

Denials carry a ONE-TIME, file-based escape hatch: `~/.local/state/wt-main-guard/allow-once.json` must contain `{"command": "<the exact command>", "reason": "<why>"}` — byte-exact match only, consumed on use, and the override itself is journaled with its stated reason. It is deliberately a file rather than an environment variable, which can be set once and forgotten, silently disarming the guard for every future command.

It strips heredoc bodies before any matching (so a heredoc body line never looks like its own standalone command), and additionally strips quoted spans before matching publish/push/merge — whose anchor words are never legitimately quoted in a real invocation — but NOT before matching `rm` targets, where a quoted target is the normal, legitimate form (`rm -rf "$HOME/tmp"`) and stripping it would blind the classifier to the exact case that matters most.

Any internal error fails open: the guard emits nothing and exits 0, on the accepted trade that a bug in this guard silently disabling it is safer than a guard that can freeze the main session on its own defect.

### `wt-pipestatus-bash-only-guard-hook.mjs` — bash-only PIPESTATUS reference warner (PreToolUse on Bash)

Warns (never blocks) when a Bash command references the bare token `PIPESTATUS` — a bash-only array. Under zsh, `PIPESTATUS` simply does not exist and any reference to it expands to EMPTY with no error, so `cmd | tee log; echo ${PIPESTATUS[0]}` silently reports nothing instead of a pipeline stage's real exit code, and `if [ "${PIPESTATUS[0]}" = 0 ]` reads as false without ever failing loudly. Verified live under zsh: `true | false; echo "${PIPESTATUS[0]}"` prints an empty string, not `1`, while the pipeline's own `$?` correctly reports `1`. The safe forms are `$pipestatus[1]` (lowercase, zsh-native, 1-indexed) or, better, redirecting the gate to a file, reading `$?`, then reading the file — shell-independent and never piped.

Measured against 163 distinct real Bash commands referencing `PIPESTATUS`, drawn from every session transcript across both this machine's config dirs and replayed against the guard's own executable as PreToolUse payloads: 163/163 fired. Reading a sample confirms the guard cannot distinguish a genuine bash-only reference from prose merely discussing the trap (a heredoc documenting the pattern, a script under test) — the same known false-positive family as the sibling guards in this directory — which is why it ships warn-only rather than blocking; a false positive there is a nag, never a lost command.

It deliberately does not cover: the zsh-correct form `$pipestatus[1]` (lowercase) — deliberately silent, that is the fix; `PIPESTATUS` appearing only in prose; a shell environment where `PIPESTATUS` is genuinely bash and genuinely correct — the guard cannot see which shell interprets a given command, so it warns unconditionally regardless of the actual shell; or any command other than a Bash tool_use.

### `wt-find-newermt-format-guard-hook.mjs` — non-ISO-8601 `find -newermt` argument warner (PreToolUse on Bash)

Warns (never blocks) when a `find … -newermt <arg>` argument is not ISO-8601. Some `find` builds (e.g. `bfs`) accept ONLY ISO-8601 timestamps for `-newermt` — a natural-language date ("5 minutes ago") is rejected on stderr, and with stderr swallowed or piped (`2>/dev/null`, `| wc -l`), the command looks like it ran clean and simply found nothing, which reads as "no recent files" instead of "the date format was rejected". Verified live on such a build: `find . -newermt "5 minutes ago" 2>/dev/null | wc -l` returns `0`, indistinguishable from a correct empty result. The safe form pipes a computed timestamp through: `find . -newermt "$(date -d '5 minutes ago' +%Y-%m-%dT%H:%M:%S)"`.

Measured against 555 distinct real `find … -newermt` Bash commands drawn from every session transcript across both this machine's config dirs, replayed against the guard's own executable as PreToolUse payloads: 256 fired. The fired population is dominated by genuine natural-language and relative forms this guard is meant to catch (`"5 minutes ago"`, `"-20 seconds"`, `"30 minutes ago"`, and similar), plus a residual class of bare shell-variable arguments (`"@$BASE"`, `"$since"`) whose actual runtime value the guard cannot evaluate — an intentionally conservative "warn when not provably safe" posture, not a design defect, since only a `$(...)` command substitution or a literal ISO-8601 string is presumed safe.

It deliberately does not cover: an argument built via `$(...)` command substitution — presumed safe, deliberately silent; a bare ISO date with no time component (`2026-08-06`) — accepted by ISO-8601-only builds, deliberately silent; a `find` build that accepts natural-language dates (GNU findutils) — the guard has no way to detect which build resolves, so it warns unconditionally; `find` invoked through a variable or wrapper script not visible in the command text itself; or any command other than a Bash tool_use. Same known false-positive family as the sibling guards in this directory: the guard reads the raw command string, so prose documenting this trap fires identically to a real invocation — harmless here because the guard only warns.

### `wt-git-commit-backtick-guard-hook.mjs` — unescaped-backtick commit-message warner (PreToolUse on Bash)

Warns (never blocks) when a `git commit`/`tag`/`notes` double-quoted `-m "..."`/`--message "..."` argument contains an unescaped backtick. Inside double quotes a backtick pair IS command substitution — the shell runs whatever sits between the backticks as a real command and splices its (often empty) stdout into the message, with no error; the commit still succeeds, so nothing fails loudly. Measured directly: `git commit -m "the default \`stretch\` applied"` ran `stretch` as a command, printed "stretch: command not found" to stderr, and committed the sentence with the word silently replaced by nothing — only reading the stored message afterwards revealed the hole.

Measured against 466 distinct real `git commit`/`tag`/`notes` Bash commands containing a backtick, drawn from every session transcript across both this machine's config dirs, replayed against the guard's own executable as PreToolUse payloads: a first pass without heredoc-awareness fired on 16/466, and reading all 16 in full showed 12 were the `-m "$(cat <<'EOF' … EOF)"` heredoc-in-command-substitution form — this project's own dominant commit convention — where the backtick sits inside a quoted-delimiter heredoc body the shell never expands, a false positive (75% of the fired set). The guard was fixed to strip heredoc bodies before matching, the same technique `wt-unquoted-tool-glob-guard-hook.mjs` already uses; re-measured against the same 466 candidates: 4/4 fired, all 4 read as genuine unescaped backtick pairs sitting directly in a plain double-quoted `-m` string (no heredoc shielding them) — 0 false positives on the corrected predicate. It still ships warn-only, not blocking: 4 true positives over 466 candidates is real signal but far short of the scale (82,015 commands) this repo requires before a guard is trusted to deny.

It deliberately does not cover: single-quoted `-m` arguments (no substitution risk — deliberately silent); the heredoc / `-F` form (the documented safe form — deliberately silent); a backtick inside a variable that is THEN interpolated into `-m` (one hop too far for a string-only guard); or any command other than a Bash tool_use (a commit issued through another tool is invisible to this hook).

### `plugin/bin/lib/guard-journal.mjs` + `wt-guard-journal-scan.mjs` — durable refusal/warning journal (shared library + standalone read CLI)

Of the eighteen `plugin/bin/*guard*.mjs` guards, sixteen now call the shared `recordGuardEvent()` helper the moment they decide to block or warn — a durable, append-only NDJSON line per event (`{ts, guard, decision, class?, reason?, cwd?}`), rotated one file per ISO-8601 week under `~/.local/state/wt-guard-journal/` (`os.homedir()`-relative, so it resolves correctly on Linux, macOS, and Windows; the `.local/state` naming is an XDG convention that still works as a plain directory on Windows, unconventional but functional). The write is `recordGuardEvent()`'s whole job and only that: `decision` must be exactly `'blocked'` or `'warned'` — a guard's own internal bookkeeping (`wt-main-guard-hook.mjs`'s pre-existing `allowed-journaled`/`override-allow` entries in its own separate journal) is out of scope by construction, never counted here. The write is fail-open: every failure mode is swallowed inside `recordGuardEvent()` so a broken journal can never be the reason a guard's own decision fails to render — proven directly by a test that points the journal at an uncreatable directory and asserts the guard's stdout is unchanged.

Two files are deliberately NOT wired to it, and the family's own test enumerates every `plugin/bin/*guard*.mjs` file (a glob, not a hardcoded list) so a future guard shipped without instrumentation fails the suite rather than going unnoticed: `wt-outbound-guard-hook.mjs` already keeps its own durable registry for a different question (spawn accounting, read via `wt-spawn-registry-scan.mjs`); `wt-stale-date-guard.mjs` is the report-generating CLI invoked by `wt-stale-date-guard-hook.mjs` (which IS instrumented), not a hook that decides block/warn on a tool call itself.

`wt-guard-journal-scan.mjs` is the read side: `node plugin/bin/wt-guard-journal-scan.mjs [--weeks N | --all] [--json]` prints a per-guard blocked/warned/total table for the current week by default. Its own output states the limit explicitly, at the same prominence as the numbers: a count is an EVENT count, not a confirmed-defect count (a guard firing on correct work writes the identical record shape to one catching a real recurrence), and only guards wired to this journal appear at all — a defect nobody has written a guard for stays invisible by construction, which mechanises recidivism (a known check firing again) and never inauguration (a brand-new class of mistake). A missing journal directory (no guard has ever fired) exits `2`; a directory that exists but cannot be read exits `3` — kept distinct from a clean zero so a read failure never silently prints as "nothing happened".

### `wt-guard-recurrence-hook.mjs` — SessionStart guard-recurrence surface (a counter nobody had to run)

`wt-guard-journal-scan.mjs` (above) answers "has a guard recurred" only when someone remembers to run it — before this hook, nothing did. This SessionStart hook reuses the same parser (`plugin/bin/lib/guard-journal-read.mjs`, extracted from the scan CLI so the two readers can never disagree) and speaks, unasked, the moment one guard's recorded firings for the current week cross a threshold: **more than twice** — i.e. 3 or more — for the same guard and the same "reason". "Reason" is grouped as (guard, `class`) when a record carries the guard's own classification field, and as one shared `(unclassed)` bucket per guard otherwise; a guard that never classifies its firings can therefore have two genuinely distinct defects cross the threshold together and read as one recurring class — a stated cost of the coarser-but-never-silently-wrong grouping, not a hidden one. What it prints is the count and the guard/class name only, never an instruction to reflect, and it carries both of the journal's own bounds every time it speaks: an event count is not a confirmed-defect count, and only guards wired to the journal are counted at all. It is silent on the common path — no guard crossed the threshold this week — and it degrades to silence rather than an error on a missing or unreadable journal directory, a malformed line, or an unrecognised record shape; a `SessionStart` hook that could interrupt a session on a bad read would get removed the first morning it misfired.

### `wt-isolated-spawn-report-path-hook.mjs` — isolated-spawn out-of-tree write-target warner (PreToolUse on Agent)

Warns (never blocks) when an `Agent` spawn carries `isolation` AND its prompt names an absolute write/report target (`write`, `save`, `report`/`REPORT_DIR`, `output` near a `/home|/Users|/tmp|/var|/opt` path) that does not already sit under a `worktrees/` directory. An agent spawned with `isolation: "worktree"` gets its own git worktree, and that tree is REAPED the moment the agent stops — a brief that names an absolute path elsewhere means the write lands nowhere, the agent's own `Write` call still succeeds (inside its own tree, at a path that merely looks right), and it honestly reports delivery. Nothing anywhere then reports the gap: an absent file and a never-written file are the same observation from the spawner's side.

It deliberately does not cover: a relative report path (fine by construction, but also invisible here); a path handed to the agent later, by message rather than in the spawn prompt; an agent that decides on its own to write outside its tree; or a target already under a `worktrees/`/`worktree/` segment, which is the correct shape and stays silent on purpose. Reasons about raw prompt prose via regex, the least reliable input available, which is why it warns rather than blocks.

### `wt-pgrep-env-dump-guard-hook.mjs` — full-listing `pgrep`/`ps` environment-dump warner (PreToolUse on Bash)

Warns (never blocks) when a Bash command uses `pgrep -a`/`-l` (or a combined short-flag cluster containing one of them, e.g. `-af`), or `ps -f`/`ps aux`/`ps -ef`/`ps -o args=` without a `-p <pid>` filter. A Bash-tool shell launched via a shell function wrapper commonly carries its own exported environment on its OWN command line — a full-listing `pgrep`/`ps` then prints every one of those `export KEY=value` pairs into the transcript, which the model then holds durably, and the call itself does not look unusual: the output is plausible-looking process-listing text, just carrying content — potentially secrets — nobody asked to see.

It deliberately does not cover: PID-only forms (`pgrep -f pattern`, `pgrep -c -f pattern`, bare `pgrep pattern`) — deliberately silent, that is the safe form; `ps -o args= -p <pid>` (a single already-identified PID, the sanctioned follow-up); a bare `ps` with no full-listing flag; or prose about this trap (a heredoc, a commit message) — same known false-positive family as the sibling guards in this file, a textual guard cannot tell code from data. The flag matcher requires the `-` to be preceded by whitespace or the string start, so a hyphenated PATTERN argument (`pgrep my-pattern`) does not itself read as a flag.

### `wt-propagation-reminder-hook.mjs` — tooling/plugin-edit propagation reminder (PostToolUse on Write/Edit/MultiEdit)

Fires, never blocks, when a `Write`/`Edit`/`MultiEdit` call lands under a `plugin/` directory, under `<config-dir>/scripts/`, or under `<config-dir>/agents/` or `<config-dir>/skills/` — the three shapes whose edits reach an audience beyond the editing session: plugin adopters, every session on the same machine, or every session sharing that config dir or project. The trigger is mechanical (a path shape); the report is judgment the hook cannot supply, so it asks four questions — who gets it, when, what changed, and whether a shipped twin needs the same fix — and never answers them. Silence means only that no matched path was touched, never that nothing needs propagating.

It deliberately does not cover `<config-dir>/rules/*.md` — `wt-rule-edit-horizon-hook.mjs` already speaks on ambient rule edits, and two reminders on one edit is how a reminder gets switched off.
