# Known issues & open items

The toolkit is **directly usable**: the committed artifacts under
`toolkit/workflows/` launch via `scriptPath` with no toolchain, and a real
39-agent review run validated the full chain end to end. Nothing below blocks
local use.

## Open items

| # | Issue | Impact | Status |
|---|---|---|---|
| 1 | **`budgetFloor` calibration is a cross-run approximation** — the semantics are implemented and tested, and a mechanism ships to ground the number in real runs, but the runtime exposes no per-agent token primitive, so tokens-per-agent stays a statistical estimate. | Floors may cut too early or too late until enough real runs accrue. | `pnpm wt:calibrate record` captures a real run's agent count + `rt.budget.spent()` + the notification token `usage`; `derive` segregates the two signals (never blends them) and prints `floor ≈ tokens-per-agent × (claims × votes + synthesis) × margin`, or an honest "no signal" rather than a fabricated number. The figure is a lower bound — refine it once ~10 real runs accrue. |
| 2 | **Phase digests are reload-only and resolved heuristically.** Each pattern emits one `[wt:digest]` `rt.log` line that `@workflow-toolbox/observe` parses into per-phase `phase.output`/`phase.choices` (handoff summaries, ghost branches, reject counts). `rt.log` is absent from the live SDK stream, so these appear on **reload only**, never live (empirically confirmed: the digest lines reach disk ONLY in the at-completion `wf_<runId>.json` — the incremental `journal.jsonl` carries only agent `started`/`result` events, never digests — so even a live FS tailer cannot surface them; making them live would need the runtime to flush `rt.log` incrementally OR re-routing digests onto an agent `result`. tracked internally). Attribution matches the digest's `stage` against the phase's agent labels and surfaces a digest only when **exactly one** resolves to a phase. | Remaining cases yield **honest absence** (no node — never a wrong one), not a crash: (a) the same pattern invoked twice under one phase title → both digests dropped (give repeated invocations distinct phases); (b) a `loopUntilDone` in an ambiguous shape — a cross-phase loop (its single digest can't pick among its ≥2 phases), OR a run with **≥2 custom-label loops** (≥2 loop digests → the marker fallback below abstains for all of them, so e.g. a multi-task `dev-implement` with one TDD loop per task still surfaces none) — stays absent; (c) a future rename of a pattern's agent-label prefix away from its `stage` string — no test catches this today (comment-only coupling). **Fixed (exactly one custom-label loop per run):** a `loopUntilDone` whose body supplies a custom `opts.label` (the single-loop `doc-rewrite` / single-task `dev-implement` shape) used to drop the `loopUntilDone:` prefix and orphan its digest; observe now attributes it via the appended `⟲` iteration marker (`isLoopIterLabel`, sourced from the shared `LOOP_STAGE`/`LOOP_ITER_MARKER` in `runtime/digest.ts`), but only when exactly one such loop digest is unresolved AND exactly one marker-bearing phase is unclaimed — so a nested pattern's digest keeps precedence and ambiguous shapes (b) fall through to honest absence. The pattern-agnostic root (a structural digest↔phase hint so any wrap-and-relabel pattern resolves without an `ingest-core` special-case) is deferred — see the generic-resolution-hint follow-up. | Mitigated by design (drop-on-ambiguity), verified on a real 7-pattern run where all phases resolved. A **real-journal integration test now locks the reload path** (`observe/test/real-journal.test.ts` reconstructs from a committed `demo-all-patterns` run journal and asserts handoff/ghosts/counts all surface — guarding drift between what the runtime writes and what observe parses, which the synthetic ingest tests cannot). The label↔stage coupling is now rename-proofed: each pattern's digest `stage` AND its agent-label prefix derive from one file-local `const STAGE`, and the cross-package counts vocabulary + loop marker are shared constants (`PatternCounts` / `PatternName` / `LOOP_STAGE` / `LOOP_ITER_MARKER` in `runtime/digest.ts`, typed across both the emit side and observe's render descriptors — a key rename is a compile break). Remaining fast-follow: a pattern-agnostic digest→phase resolution hint so observe's generic ingest needn't special-case `loopUntilDone` . |
| 3 | **The tool-denial / degraded-run indicator is a precision-first heuristic, and its absence is shown as "clean".** `classifyDenial` matches a CLOSED allow-list of three grounded English denial wordings (auto-mode classifier / generic rejection / PreToolUse hook), gated on `is_error===true` — precision over recall, so an ordinary tool error never false-alarms. observe-ui surfaces it on **reload only** (denials are transcript-derived, not in the journal or live SDK stream): a run-level ⚠ DEGRADED pill + per-phase ⚠ badge + the `wt-report`/zip "Tool denials" section, all driven by the same scan. | If Claude Code ever changes a denial's wording, the matcher returns null and a genuinely-blinded run renders with **no** indicator — and because the UI shows degraded-ness only when detected, that absence reads as a positive "clean" (a false assurance, the dangerous direction). Per-phase badges also can't place a denial on a **phaseless/unattributed** agent (the run-level pill + the panel's "(unattributed)" group still count it). | Mitigated, not eliminated: the wordings are unit-pinned to the exact captured strings (`debugger/test/tool-denial.test.ts`), the `ingest()→denials` path is now covered (`observe/test/ingest-fs.test.ts`), and both the single-run and the **pipeline combined view** thread the same report so the UI and the downloadable report agree. A live wording-drift would still pass silently — re-running the **`upgrade-canary`** after a Claude Code upgrade is the intended trip-wire; treat a sudden drop to "no denials ever" on a run you watched get blocked as the signal to re-ground the allow-list. |
| 4 | **Multi-observe (`wt-observe start`, 1 or 2+ sources): a `CLAUDE_CONFIG_DIR` shared across OS users is unsupported.** The one observe server's per-user state (pidfile, log, and per-source pipeline/gate `spikeDir`) lives under the per-OS state root (`observeStateRoot` — Linux XDG, macOS `~/Library/Application Support`, Windows `%LOCALAPPDATA%`), keyed path-only (`server.json`/`server.log`, per-source `spikeDir` keyed by `configDirKey`), never UID-scoped (ADR 0009's D3). | Two OS *users* pointed at the SAME config dir would silently share pidfile/log/spike state — a spawn/adopt race, or a cross-user pipeline-manifest collision, that nothing here detects or refuses. | By design, not a bug: one observe server per OS user is the only supported shape. Documentation-only — no code here checks for or rejects a shared config dir; this is a boundary to respect, not a mitigated failure mode. |
| 5 | **Windows/macOS support  ships with accepted platform semantics, untested on real hardware.** (a) `chmod 0600/0700` on the pidfile/state dirs is a near-no-op on Windows (NTFS ACLs, not POSIX modes) — the pidfile's API token is protected by the user-profile ACL of `%LOCALAPPDATA%`, not by mode bits. (b) `wt-observe stop`'s SIGTERM is a HARD terminate on Windows (no graceful-shutdown signal exists) — the server's exit-path cleanup (vite-watcher reap, SDK-child reap) does not run there. (c) The win32 PID-identity probes shell out to PowerShell (~1s per probe) — `status`/`start`/`stop` are that much slower. (d) An npm-installed `claude.cmd` shim is NOT found by the bare-`claude` PATH probe (CreateProcess resolves `.exe` only) — set `CLAUDE_BIN` to the shim's `.cmd` path explicitly instead (as of the cross-OS CI fixes, `resolveClaudeRuntime` spawns a `.cmd`/`.bat` `CLAUDE_BIN` via `shell:true` — previously this also silently fell through, same as the bare-PATH gap). | Mac/Windows users get native state/config locations, working spawns and recycled-PID protection, but the four semantics above differ from Linux, and none of this has run on a real macOS/Windows machine yet. | Code paths are unit-tested via injected `platform`/parsers; the impure probes are best-effort with 3s timeouts (degrade to identity-unknown, the safe direction). Validated since: a cross-OS CI matrix (`.github/workflows/cross-os.yml` — full test suite + lifecycle smoke on real windows/macos/ubuntu runners) AND an end-to-end native-Windows session (2026-07-08: native state root, PID identity, real-credential launch with live DAG, terminal-close survival — see `docs/public/windows-native.md`). macOS still lacks a real-credentials manual pass; semantics (a)-(d) remain by-design differences. |

| 6 | **A live ATTACHED run's agent→phase ASSIGNMENT materializes at completion unless prompts carry `wt-meta` tags.** The phase SKELETON itself now renders from t0 for every local launch mode: inline and named launches read `meta.phases` from the persisted script copy (`<session>/workflows/scripts/<name>-<runId>.js` — the parser accepts both the toolkit's pure-JSON meta and JS-literal metas: bare keys, single quotes, trailing commas, comments), and `scriptPath` launches read it via the launch `tool_result` pointer in the session transcript. But the incremental `journal.jsonl` still carries only agent `started`/`result` events — no mid-run phase membership. | Without prompt tags, a live attached run shows its phase columns but agents pile into "(no phase)" until completion, when the `wf_<runId>.json` journal backfills the assignment. Two shapes stay skeleton-less for their whole live duration: externally-attached runs (unknown session) and launches older than the transcript-tail window. | Live assignment works when agent prompts start with a `<!-- wt-meta label="…" phase="…" -->` line — `@workflow-toolbox`-built artifacts emit it automatically (`withPromptTags`), and hand-written scripts can add it manually; rebuild pre-tag artifacts to pick it up. The rest is an upstream data gap (the journal would need mid-run phase events). Server-launched runs are unaffected (full SDK stream). Reload-during-live no longer loses the shape for REGISTRY runs (recall falls back to the in-memory snapshot + SSE re-attach, ). |

| 7 | **Hub federation (ADR 0010) ships with deliberate scope limits.** (a) **No remote liveness rollup** — `/api/sources` and hub `/api/health` mark a remote `remote:true` without pre-probing it, so a stopped/partitioned remote still renders in the switcher and only fails when you actually browse it (an honest 502, or up to a ~30 s connect hang on a dead Windows→WSL socket); `wt-observe status` classifies only the hub's OWN health, not federation health. (b) **Loopback-only** — the control plane binds 127.0.0.1; a remote beyond localhost (WSL forwarding, or an SSH tunnel to a dev box) is the only reachable shape. A LAN/remote-machine hub would need an explicit non-loopback bind, deliberately not offered. (c) **Federation depth is 1** — a remote that is itself a hub is exploded into its LOCAL sources at boot (health probe); the remote's OWN remotes are skipped (no transitive chains/loops). A remote hub added AFTER this hub booted is only re-explored on a hub restart. | You see every world in one window, but a dead remote is a lazy discovery (browse-time, not status-time), remotes must be loopback-reachable, and hub-of-hubs is one level deep and boot-time-resolved. | By design (ADR 0010): the honest 502 + the switcher entry are the liveness signal; loopback is the security boundary the whole control plane rests on; depth-1 avoids proxy loops. A remote liveness rollup on `/api/sources` is the natural fast-follow if the browse-time failure proves annoying. |

| 8 | **Desktop packaging: mac unsigned/untested, Windows nsis needs a native build.** The Linux AppImage is built AND e2e-verified (playwright `_electron` under WSLg on the packaged executable). The Windows x64 **zip** cross-builds from WSL (SDK is JS-only → platform-agnostic app.asar, byte-identical to the proven Linux one) but is NOT GUI-verified off-Windows; the Windows **nsis installer** needs wine to cross-build, so build it natively (`pnpm --filter @workflow-toolbox/observe-desktop pack:win` on the Windows host). The **mac dmg** config is present but unsigned and unbuilt (no macOS here) — an unsigned dmg is local/dev use only, no notarization. | A Windows user runs the zip's `workflow-observe.exe` directly (verified structurally, not by pixels off-Windows); a mac user must build + accept an unsigned app themselves. | Accepted delivery boundary: the JS-only SDK makes the cross-built Windows zip structurally correct (no wrong-OS binary — no SDK binary is shipped at all; live launches drive the installed `claude`). Signing/notarization + a CI packaging matrix are the fast-follow. |

## External limitations — mitigated, not fixable here

| # | Limitation | Mitigation |
|---|---|---|
| A | **The Workflow tool is a research preview**; part of the surface the toolkit relies on (`isolation`, `label`, `budget`, the determinism bans, the 512 KB cap) is verified against the binary, not officially documented. An upgrade can change it. | Firewalled behind `@workflow-toolbox/runtime` — exactly one package changes. Re-verify after upgrades; the `upgrade-canary` skill does exactly this. |
| B | **Silent exclusion over 512 KB** on the `name` path: an oversized file in `.claude/workflows/` is simply never registered — no error anywhere. | `workflow-toolbox build` warns from 400 KB and throws at 512 KB. Hand-edited artifacts past the cap remain a blind spot. |
| C | **The name registry refreshes lazily** — invocation by `name` can fail right after install. | Use `scriptPath`, which is always reliable; documented in the README. |
| D | **Agents die mid-reasoning at context limits — systematically.** Several occurrences during development; the dying agent's last mid-thought text arrives as a normal-looking completion. | The four defence layers encoded in the examples + README: a schema at every consumed boundary, fresh-evidence verification, decomposed agent scopes, and `WorkflowOutput.error` + `resumeFromRunId`. A discipline, not a fix. |
| E | **Top-tier model alias availability is environment- and time-dependent** (plan tiers, access windows, provider policy — `'fable'` has already gone through availability churn) — a verifier (or any agent) pinned to an alias that is not callable where the run executes errors at runtime. | `BEST_MODEL` tracks the strongest *reliably-callable* tier (currently `'opus'`), so `adversarialVerification` verifiers default to a safe tier; the toolkit never pins a volatile alias itself. Verify an alias is callable in the run environment before hand-overriding any `model`/`verifierModel`; bump `BEST_MODEL` when the reliably-callable tier changes. |
| F | **`dev-implement` `{artifactPath}` very-large-file fidelity** — in `artifactPath` mode the PlanArtifact is read by an agent (the sandbox has no filesystem) and returned through the agent's output. A very large artifact (the JSDoc cites ~60 KB as the motivating case) could in principle be truncated or reworded by the agent. | **Fails loud, never silent-wrong**: a truncated read yields invalid JSON (caught at `JSON.parse`) and structural corruption is caught by the same `validateArtifact`/`validateGraph` gate the inline path uses. The only undetectable residue is a paraphrased *string* field that still parses, whose blast radius is a slightly degraded implementer prompt (the fresh-evidence checker reads real test output, not the prompt). If a large artifact intermittently fails to load, re-run, or inline it via `{ artifact }`. **Path base**: an absolute `artifactPath` is unambiguous; a relative one resolves against the read agent's cwd (the Claude Code session dir, verified live 2026-06-21), *not* the artifact's `projectDir` — prefer absolute. |
